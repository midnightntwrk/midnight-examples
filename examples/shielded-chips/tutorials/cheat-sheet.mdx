# Shielded-token cheat-sheet

A reference for the operations and rules this tutorial uses. Each one is explained where it first
appears, in [the chips token](/tutorials/shielded-chips/chips-token) or
[the roulette contract](/tutorials/shielded-chips/roulette).

## Operations

| Operation | Function | Coin in | Coin out |
|-----------|----------|---------|----------|
| Create a coin | `mintShieldedToken(domainSep, value: Uint<64>, nonce, recipient)` | none | `ShieldedCoinInfo` |
| Derive a token color | `tokenType(domainSep, contractAddress)` | none | `Bytes<32>` |
| Fresh nonce from a seed | `evolveNonce(index: Uint<128>, seed)` | none | `Bytes<32>` |
| Accept an incoming coin | `receiveShielded(coin)` | `ShieldedCoinInfo` | `[]` |
| Store a coin in a ledger `Map` | `map.insertCoin(key, coin, owner)` | `ShieldedCoinInfo` | stored as `QualifiedShieldedCoinInfo` |
| Spend a coin already in the tree | `sendShielded(coin, recipient, value: Uint<128>)` | `QualifiedShieldedCoinInfo` | `ShieldedSendResult` |
| Spend a coin created in this transaction | `sendImmediateShielded(coin, recipient, value: Uint<128>)` | `ShieldedCoinInfo` | `ShieldedSendResult` |
| Combine two coins | `mergeCoin(a, b)` | two `QualifiedShieldedCoinInfo` | `ShieldedCoinInfo` |
| Destroy a coin | send to `shieldedBurnAddress()` | | |
| Commit to a coin | `persistentCommit<...>([nonce, color, value], salt)` | none | `Bytes<32>` |
| This contract's address | `kernel.self()`, wrapped with `right(...)` | | |
| Caller's wallet key (a witness) | `ownPublicKey()`, wrapped with `left(...)` | | |

`tokenType` in a circuit and `rawTokenType` in TypeScript compute the same color, so a deployer
can learn a token's color without a transaction.

The spend-path rule: a coin whose commitment was created by an output of the **current**
transaction is not in the global tree yet, so it is spent as a Zswap transient, at `mt_index: 0`.
A coin already in the tree needs `sendShielded` and its real `mt_index`. In the standard library
this repo pins (0.31.1), `sendImmediateShielded` is exactly `sendShielded` with `mt_index: 0`, so
`claimWinnings` can `sendShielded` the coin `mergeCoin` just created. `_burn` uses
`sendImmediateShielded` for that case, as MIP-0011 asks, because its `ShieldedCoinInfo` parameter
can't carry a caller-supplied index. Prefer `sendImmediateShielded` when you write a same-tx spend:
it states the intent.

## Types

- `ShieldedCoinInfo` is `{ nonce, color, value }`: a coin in hand, such as one created or
  received in this transaction.
- `QualifiedShieldedCoinInfo` is `{ nonce, color, value, mt_index }`: a coin the ledger has
  already committed, spendable with `sendShielded`. In this example `mt_index: 0` appears only for
  a coin received or created in the current transaction, such as the merged payout coin in
  `claimWinnings`.
- `ShieldedSendResult` is `{ change: Maybe<ShieldedCoinInfo>, sent: ShieldedCoinInfo }`.
- Recipients are `Either<ZswapCoinPublicKey, ContractAddress>`: `left` is a wallet key and `right`
  is a contract address.

## Privacy rules, in one place

- **Coin values in a transfer never reach public state.** A send publishes a commitment, not an
  amount.
- **Mint amounts do.** `mintShieldedToken` records the value in the transaction's shielded-mint
  effects. Minting hides the recipient, not the amount.
- **Circuit arguments are not published.** A `ZswapCoinPublicKey` passed as an argument does not
  appear on chain.
- **Ledger reads and writes are what publish**, along with the transaction's effects, such as
  mint amounts. An exported circuit's return value is not published: the transaction carries only
  a randomized commitment to the call's inputs and outputs. `disclose(...)` is a compiler
  acknowledgment at a trust boundary, not a statement that a value went on chain. Read the state
  to find out which values did.
- **Never write a user's coin nonce to public state.** It identifies the wallet that funded the
  coin and the wallet paid out of it. Store a commitment and reopen it from a witness.
- **`sendShielded` and `mergeCoin` derive the output nonce from the input nonce alone**, and
  `mergeCoin` from its *first* argument. Ordering is a privacy decision, and derivation chains are
  only as private as their root.
- **A `receiveShielded` argument is a new coin: give it a fresh nonce.** Build it with
  `freshCoin(color, amount)` (or the ledger's `createShieldedCoinInfo`), never from
  `availableCoins`. The wallet pays for it and makes change. Then storing it publicly links to no
  wallet, which re-sending it to `kernel.self()` never fully achieved.
- **A public nonce still leaks outbound.** Whoever you pay out of a coin whose nonce is public is
  confirmable, fresh nonce or not. Keep coins you will pay players from out of public state.
- **A caller-chosen map key needs a `member` check** before `insertCoin`, or a colliding deposit
  overwrites an entry and strands its coin.
- **A pseudonym is only as private as the coins recorded under it.** An unrelated `sk` is necessary
  and not sufficient.
- **Burn amounts are private until you count them.** A bare burn publishes only commitments.
  MIP-0011's supply counter write is the one thing that puts the amount in the transcript. An
  on-chain `totalSupply` and private burn amounts are mutually exclusive, so pick deliberately.
- **A derived nonce is a public nonce.** MIP-0011's derived-nonce mint is *recipient-public* by its
  own documentation, because its inputs are public ledger state. Use a caller-supplied secret
  nonce when recipients matter.

The audit behind these rules, including the first fix that turned out to be wrong, is in
[`LESSONS.md`](https://github.com/midnightntwrk/midnight-examples/blob/main/examples/shielded-chips/LESSONS.md).
