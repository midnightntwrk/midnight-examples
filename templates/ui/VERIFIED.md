# What was actually verified in the generated UIs

Don't claim more than this when you reuse a pattern from one of these UIs.

**CI covers the rest for every UI.** It runs `yarn new:ui <name> --check`,
typecheck, unit tests and a production build (verification checklist steps
1–4 in `AGENTS.md`). The table below is only what CI can't run: the page in a
real browser, and a person approving deploys and calls in Lace.

The table is generated from each UI's `ui/verification.json`; don't edit it
here. After running a step, set its `status` (`verified`, `partial` or
`not-run`), `date` and `notes` (exactly what ran) in that file, then run
`yarn new:ui <name> --sync`. `--check` (and so CI) fails when the table is
stale, when a `verification.json` is malformed, or when one says the Lace
calls are verified while its `ui/README.md` still has the "TODO: end-to-end
verification with Lace" checklist. That checklist is how each UI's Lace steps
get run; delete it once every item is ticked.

## Never run anywhere

- Wallet-delegated proving.
- A second browser profile joining.
- Re-joining after a reload through the passphrase card in the full app.

## Template pieces checked only by unit tests and CI builds

No real transaction has gone through these yet:
- the deploy-input slot and non-destructive re-join;
- generic circuit forms, including **Use my address** (`userAddress`), **Use
  my key** (`coinPublicKey`), the shielded-coin picker (`shieldedCoin`,
  `lib/coin-book.ts`) and the return-value line;
- `<WalletBalancesCard>`, including whether the connector's balance keys
  match the hex colors it labels;
- the funding hint's `mn_addr_` argument in `<DeploymentCard>`.
